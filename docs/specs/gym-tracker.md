# Spec: Gym Tracker (first module of personal-app)

Date: 2026-09-19 · Status: approved

## 1. Goal

A personal API at `api.akhmadqasim.com` for a single user, plus an iOS app.
The first module tracks gym training: equipment, training days, weight,
reps. The iOS app works offline-first and replicates its data to the server.
The system is a *modular monolith* because more modules (server management,
network tooling, …) will follow.

Language: the app, catalog names, API error messages, code, comments and all
repo documents are in English.

Repository: `personal-app` (public, monorepo).

```
personal-app/
├── api/          Rust Worker (this spec)
├── ios/          SwiftUI app (separate spec, later)
├── docs/specs/   design specs
├── docs/plans/   implementation plans
├── CLAUDE.md, .claude/rules, .claude/skills
└── .github/workflows/
```

## 2. Technical decisions

| Topic | Choice | Why |
|---|---|---|
| Language | Rust (`workers-rs`, compiled to WASM) | Toolchain already on the PC; low resource usage |
| Hosting | Cloudflare Workers + D1 + R2 | Free tier, automatic TLS, domain already on Cloudflare |
| Deploy | GitHub Actions → `wrangler deploy` | Automatic on every push to `main` |
| Auth | Static bearer token (Worker secret) | Single user; token lives in the iOS Keychain |
| Sync | Row-level last-write-wins + `seq` cursor | Robust for one user / one or two devices, minimal machinery |
| Client | iOS 26, SwiftUI, GRDB (SQLite) | Local schema identical to the server |

Auth upgrade path if ever needed: put Cloudflare Access in front of the
Worker without touching code. No `*.workers.dev` subdomain is exposed.

## 3. Data model

Every synced table has these base columns:

```sql
id         TEXT    PRIMARY KEY,          -- UUID v4, generated by the client
updated_at INTEGER NOT NULL,             -- epoch ms, set by the client on write
deleted_at INTEGER,                      -- soft delete; NULL = active
seq        INTEGER NOT NULL UNIQUE       -- set by the server, monotonic, pull cursor
```

Gym tables (order = foreign-key dependency order):

| Table | Domain columns |
|---|---|
| `exercise` | `name`, `muscle_group`, `equipment`, `image_key` NULL, `notes` NULL |
| `program` | `name`, `is_active` (0/1) |
| `program_day` | `program_id` → program, `name`, `position` |
| `program_exercise` | `program_day_id` → program_day, `exercise_id` → exercise, `position`, `target_sets`, `target_reps`, `target_weight_kg` NULL, `rest_seconds` NULL |
| `workout_session` | `started_at`, `finished_at` NULL, `program_day_id` NULL → program_day, `notes` NULL |
| `workout_set` | `session_id` → workout_session, `exercise_id` → exercise, `position`, `weight_kg` REAL, `reps`, `rpe` NULL, `completed` (0/1) |

Enums: `equipment` ∈ barbell, dumbbell, machine, cable, bodyweight, other.
`muscle_group` ∈ chest, back, shoulders, biceps, triceps, forearms, core,
quads, hamstrings, glutes, calves, full_body, cardio, other.

Usage flow: open a program day → the app copies `program_exercise` rows into
`workout_set` rows, prefilling `weight_kg`/`reps` from the last set of that
exercise → the user edits → save locally → sync.

`seq` comes from one global counter (`sync_meta(key, value)`, key
`last_seq`) so ordering is consistent across tables.

### Built-in catalog

A seed migration fills `exercise` with a standard catalog (canonical English
names such as "Lat Pulldown", "Leg Press") using fixed UUIDs,
`updated_at = 0` (so any user edit wins) and `image_key = "builtin/<slug>"`.
The iOS app receives the catalog through its first pull (`since_seq = 0`);
nothing is embedded in the app.

### Images

- **Built-in**: `image_key` starting with `builtin/` → the app renders a
  bundled illustration in one consistent style; nothing goes through the API.
- **Custom**: the user photographs equipment → the app downsizes to ≤1024 px
  JPEG → `PUT /api/gym/exercises/{id}/image` → the server stores the object in
  R2 under `exercises/<exercise_id>/<millis>-<nonce>.<ext>` and returns
  `image_key`; the app writes `image_key` into its local row and syncs it like
  any other column (the server never touches the row). Images are read via
  `GET /api/gym/images/{key}` (auth required, `Cache-Control: private,
  max-age=31536000, immutable`). Limit 5 MB; types `image/jpeg`, `image/png`,
  `image/webp`. Orphaned objects in R2 are left alone.

## 4. Endpoints

```
GET  /api/health                         200 {"ok":true}                 no auth
POST /api/sync                           two-way replication             Bearer API_TOKEN
GET  /api/gym/export                     JSON of all active gym rows     Bearer API_TOKEN
PUT  /api/gym/exercises/{id}/image       upload photo → {"image_key"}    Bearer API_TOKEN
GET  /api/gym/images/{key}               read photo from R2              Bearer API_TOKEN
```

There is no per-table REST CRUD: the app reads and writes local SQLite and
`/api/sync` is only the replication channel. Future *action* modules (e.g.
`servers`) use ordinary REST under `/api/<module>/…`.

Every error response has the shape `{"code": "<snake_case>", "message": "…"}`
with a matching HTTP status: 400 `bad_request`, 401 `unauthorized`, 404
`not_found`, 409 `conflict`, 413 `payload_too_large`, 415
`unsupported_media_type`, 422 `validation_failed` (plus
`errors: [{table, id, message}]`), 500 `internal`.

## 5. Sync protocol

Request `POST /api/sync`:

```json
{
  "since_seq": 1234,
  "push": {
    "exercise":    [ { "id": "…", "name": "…", "updated_at": 1758000000000, "deleted_at": null } ],
    "workout_set": [ ]
  }
}
```

The server processes the push in **one atomic D1 batch**, tables ordered by
FK dependency. Per pushed row:

1. Not in the DB → insert, new `seq`.
2. Exists and `push.updated_at > db.updated_at` → overwrite all columns, new `seq`.
3. Otherwise → ignore (server wins).
4. Validation failure (`reps <= 0`, `weight_kg < 0`, missing FK target,
   unknown enum value, missing required column, unknown table) → 422 with a
   list of `{table, id, message}`; the whole batch is rejected.

A push is limited to 500 rows (413 otherwise; the client chunks).

`seq` allocation: read `last_seq`, number the pushed rows
`last_seq+1..last_seq+N`, and write `last_seq+N` back inside the same batch.
Because `seq` is UNIQUE, two concurrent syncs make the second batch fail →
409 `conflict`, the client retries.

After the push the server returns rows from all tables with
`seq > since_seq`, ordered by `seq`, at most **500 rows in total**; if
truncated, `has_more = true` and `seq` = the `seq` of the last row sent, and
the client loops. Rows just pushed are echoed back (idempotent; the client
applies the same LWW rule).

Response:

```json
{ "seq": 1300, "has_more": false, "pull": { "exercise": [ ], "workout_set": [ ] } }
```

Client rules:

- Every local write: `dirty = 1`, `updated_at = now`.
- On success: clear `dirty` only on rows whose `updated_at` did not change
  during the request; store `since_seq = response.seq`.
- On failure: retry; the request is safe to repeat.
- Deletion is always a soft delete; nothing is hard-deleted on either side.
- Chunk pushes in FK order (parents in the same or an earlier chunk than their
  children); an FK violation is a 422 the client cannot repair by retrying.
- A pushed row the server ignores (rule 3) is not echoed unless its server
  version has `seq > since_seq`; this is safe because the client only holds a
  cursor past a row it has already applied, so clearing `dirty` on unchanged
  `updated_at` cannot lose a newer server version.

Rules 1–3 are one `INSERT … ON CONFLICT(id) DO UPDATE … WHERE
excluded.updated_at > <table>.updated_at` statement generated by the sync
engine from each table's column description. The SQL builder and validation
are pure functions unit-tested without Cloudflare.

## 6. Repository layout (`api/`)

```
api/
├── Cargo.toml                 # dependencies + [lints]: clippy pedantic, unwrap/expect denied
├── rustfmt.toml
├── package.json               # wrangler as a devDependency (dev & tests)
├── wrangler.toml              # worker name, D1 + R2 bindings, route api.akhmadqasim.com
├── migrations/                # 0001_gym.sql, 0002_gym_seed.sql
├── src/
│   ├── lib.rs                 # #[event(fetch)] → router
│   ├── router.rs              # auth gate, /api/health, /api/sync, module routes, 404
│   ├── auth.rs                # bearer token, constant-time comparison
│   ├── error.rs               # ApiError → JSON
│   ├── db.rs                  # thin D1 helpers (serde_json ↔ JsValue)
│   ├── sync/{mod,table,sql,handler}.rs
│   └── modules/
│       ├── mod.rs             # registry: sync tables + routes of every module
│       └── gym/{mod,tables,validate,export,images}.rs
└── tests/api/
    ├── main.rs                # custom harness: start wrangler dev → run trials → stop
    ├── server.rs              # spawn `wrangler dev` with local D1/R2, apply migrations, kill tree
    ├── client.rs              # HTTP helper + trial builder
    ├── fixtures.rs            # row builders
    ├── health.rs, auth.rs, sync.rs
    └── gym/{mod,validation,catalog,export,images}.rs
```

Module contract: a module exposes its `SyncTable`s (name, columns, validator,
FK order) and optionally extra routes. The sync engine knows nothing about
module internals.

## 7. Testing

- Unit tests (`cargo test --lib`): SQL builders, row validation, token
  check, error serialization.
- Integration tests (`cargo test --test api`): a custom harness starts
  `wrangler dev` with local D1 + R2 (state in `.wrangler/test-state`, wiped
  each run) and exercises real HTTP: health, auth rejected/accepted,
  push–pull, idempotency (same push twice → same result), LWW conflict, soft
  delete, `has_more` pagination, 422 rejecting the whole batch, missing FK,
  unknown table, oversized push, built-in catalog on first pull, export,
  image upload/read, oversized/wrong-type image rejected, path traversal.
- Every feature ships with tests; red CI blocks merge.

## 8. CI/CD and operations

- Secrets: `API_TOKEN` (Worker secret, `wrangler secret put`);
  `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` (GitHub Secrets; token
  scopes: Workers Scripts Edit, D1 Edit, R2 Edit, Workers Routes Edit on the
  zone).
- `api-ci.yml` (PRs and pushes touching `api/**`): `cargo fmt --check` →
  `cargo clippy --all-targets -D warnings` → unit tests → integration tests.
- `api-deploy.yml` (after CI succeeds on `main`): `wrangler d1 migrations
  apply DB --remote` → `wrangler deploy`. Rollback: `wrangler rollback`.
- Backup: D1 Time Travel (30 days) plus the full copy in the iOS SQLite.
